## 1. Where the brief and the code disagree

1. **Multi-tenant is a decision, not an implementation.** The code is single-tenant: a second
   `POST /organizations` returns 409 `ORGANIZATION_ALREADY_EXISTS` ("only one is supported"); users have no
   organization link; `PROJECT_VISION.md` still describes one deployment per customer.
2. **"Amount Mismatch not built" is wrong.** The live pipeline emits `SETTLEMENT_AMOUNT_MISMATCH` and
   `INCORRECT_COMMISSION` (15,000-row probe: 276 mismatches). Five categories exist, not three. They only fire
   when a commission contract applies (see §5-A).
3. `PROJECT_STATUS.md` is stale (says 16 modules / 217 tests; actual 18 modules / 253 tests).
   `reconflow_results_endpoints.diff` is a stray committed file in the backend repo.
4. Minor: `seed.py` logs with a malformed format string (`"Seed owner 's' already exists..."` + arg).

## 3. Correctness of the numbers

Verified from code and probe runs:

- **N1** `total_potential_revenue_leakage` sums *all* categories, including `UNEXPECTED_SETTLEMENT` (money the
  restaurant *received*). Probe: 6,039.50 headline of which 2,046.50 was Unexpected Settlement.
- **N2** Amount/commission variances use `abs()`; direction is lost, so **overpayments count as loss**.
  Probe: 276 overpayments of +3 = 828.00 reported as leakage.
- **N3** Missing Settlement loss = gross POS amount, not net of commission; a platform will pay net.
- **N4** Cancelled After Preparation is a substring match on free-text POS status (`cancel`/`refund`/`void`).
  Refund/void are not "cancelled after preparation"; POS status doesn't say who cancelled; the app's own
  recommended-action text says it is "likely not a payment dispute".
- **N5** The POS file has no channel column, so dine-in and other-platform orders appear as Missing Settlement.
  Branch+platform scoping alone does not fix this; it needs a per-branch-platform POS source label
  (or a POS channel column).
- **N6** Contract lookup keys on `analysis.branch_id` only; a branch active on two platforms has two active
  contracts → ambiguous → `None` → the commission/amount checks are silently skipped for every order.
- **N7** `discrepancy.estimated_loss` is `Numeric(14,2)`; KWD uses 3 decimals (Kuwait is a target market).
  Tolerance floor is a flat 1.00 (large for KWD). Low priority, flag when Kuwait onboards.
- **N8** Current dispute PDF (client-side `generateDisputeReport.ts`): lists *all* discrepancies including
  Unexpected Settlement; "Total claimed" = the overstated headline; "Requested action" column is
  second-person advice inside a document addressed to the platform.

## 4. Measured performance (SQLite, in-process; Postgres adds per-statement network latency)

Synthetic data, fixed seed, 3% missing settlements, 2% amount mismatches, repeating price points.

| Orders | Stage | Time | SQL statements |
|---|---|---|---|
| 1,000 | comparison | 1.04 s | 3,901 |
| 4,000 | comparison | 3.87 s | 15,596 |
| 15,000 | comparison | 16.22 s | 58,183 |
| 15,000 | discrepancies / GET discrepancies (736 rows) | 0.89 s / 0.30 s | 930 / 1,476 |
| 15,000 | validate, normalize, match (exact refs) | 0.2 / 1.7 / 2.3 s | ≤ 26 each |

Matching when exact reference matching finds nothing (platform refs carry a prefix), fallback path:

| Orders | Matching time |
|---|---|
| 1,500 | 1.21 s |
| 3,000 | 3.88 s |
| 6,000 | 14.89 s |

Reading: comparison does ~4 statements per matched order (N+1); GET discrepancies ~2 per row; fallback
matching grows ~4× per doubling (quadratic). Routes are `async def` calling blocking sync code, so a long stage
can stall other requests (inferred from FastAPI semantics; concurrency **not** load-tested). Everything else is
cheap. The frontend polls status; during a 16 s stage every other client's poll waits.

## 5. Addenda from round 2

### A. Do mismatch / commission checks need a contract? — Yes (verified)
Without a commission contract, every matched pair is skipped: probe with 973 matched pairs →
`skipped_no_contract_count: 973`, 0 mismatch/commission discrepancies (27 vs 50 discrepancies with a contract).
The count exists on the comparison-run response but **is not in the results summary or UI**. Same silent skip
for ambiguous contracts (N6). Fix: surface "N orders not checked — no/ambiguous contract" in results and UI.

### B. Uploaded-file storage
Local-disk encrypted storage (`./reconflow_files` default). Render disks require a paid service, attach to a
single instance, disable zero-downtime deploys, and snapshot daily (Render docs, disks page). If prod has no
disk (*unverified*), uploaded originals **and generated reports** (same storage) vanish on redeploy while
results rows stay in Postgres. Also confirm `RECONFLOW_ENCRYPTION_KEY` is stable across deploys.
**Recommendation: S3-compatible object storage.** `FileStorage` is already an ABC and files are Fernet-encrypted
before being written, so this is one new class with the same interface; keys `org/{org_id}/…`; choose the bucket
region deliberately (GCC clients may care where financial data sits). Disk is the stopgap only.

### C. Claim-letter language and the PDF library
Whether platforms require Arabic is a business fact I cannot verify; confirm via a real dispute channel.
Test run: **WeasyPrint 70.0** in the sandbox rendered a bilingual EN/AR page with correct Arabic shaping,
RTL paragraph and RTL table column order (one page, DejaVu Sans, rasterized and inspected). Production needs
an embedded Arabic font (e.g. a Noto Naskh/Amiri-class font, to be chosen and bundled) and Pango on the host
(likely a Docker deploy on Render — *unverified*). Recommendation: server-side WeasyPrint with HTML/CSS
templates regardless; letter language becomes a template parameter, so Arabic is later a template, not a rewrite.

### D. Safe way to run the 100k-order test
1. Never against prod, never via n8n/ngrok; call the API directly. Synthetic data only, fixed seed.
2. Throwaway Postgres of the same major version as prod (local Docker, or a temporary Render DB in the API's
   region deleted afterwards). Not the free tier — its throttling invalidates results.
3. Ramp 10k → 25k → 50k → 100k on a fresh DB each step with `timeout` (e.g. 120 s per stage) so a runaway stops.
4. Realistic inputs: reference-prefix mismatch (forces fallback matching), heavy duplicate amounts, time skew,
   cancelled statuses, orders from several platforms, 3% missing / 2% mismatched.
5. Run the API under the intended memory limit (e.g. `docker run --memory`), record peak RSS, statements per
   stage (`pg_stat_statements`), `EXPLAIN (ANALYZE, BUFFERS)` on hot queries, and p95 latency of a concurrent
   `GET /analyses/{id}` poller during the heavy stage (proves or refutes event-loop stalls). Add 5 concurrent analyses.
6. File size: ~3.5 MB per file at 100k rows (extrapolated from 0.53 MB at 15k) — check the cap in `imports/security.py`.

3. **n8n.** Cannot list node changes without the workflow JSON (pending). API-level changes: pass the user's token

4. **AI report editor.** Prompt is soft; the hard control is structure + post-check: narrative stored as separate
   fields; reject any output containing digits/dates/order refs outside the locked data (the AI Insights module
   already uses a number post-check pattern). Backend system prompt sent on every call.
5. **Render sizing.** Plan unverified. Render's docs: free Postgres is fixed at 1 GB and expires after 30 days;
   free web services sleep when idle; paid Postgres storage is billed per GB. Free tier is unfit for paying
   clients. At dozens–low hundreds of clients, DB size is not the first limit — the N+1 / quadratic code paths

7. **History page.** New endpoint (none exists) + persisted total on the analysis.
8. **Dispute letter.** Keep: locked table, internal/external split, narrative-only AI editing. Change: server-side
   generation with stored version + hash; claim only underpayments net of commission; Cancelled off by default

9. **Deployment.** Blockers: n8n on a Windows machine behind ngrok; `RECONFLOW_ALLOWED_ORIGINS` (defaults to

## 7. Batch 1 design proposal (AWAITING APPROVAL — nothing implemented)

Scope: close `POST /users`; require a token and enforce org/branch scope on every route; stop the n8n path
bypassing per-user access; add Alembic. Role decisions from the user are in `DECISIONS.md`.

**7.1 Model.** Add `PLATFORM_OPERATOR` to `UserRole` (native PG enum → `ALTER TYPE … ADD VALUE`, run outside a
transaction block). Add `users.organization_id` (nullable FK) with CHECK
`(role = 'PLATFORM_OPERATOR') = (organization_id IS NULL)` — a client user cannot hold the operator role even by
a direct DB mistake. Operators are created only by a CLI/seed command, never over HTTP. Add
`audit_log.organization_id` so non-operators read only their own org's entries.

**7.2 Visibility.** Operator: all orgs. OWNER: all branches of own org, evaluated per request (future branches
included, no grants needed). FINANCE_MANAGER / ACCOUNTANT / OPS_MANAGER / AUDITOR: only `user_branch_access`
rows, and a grant is only allowed if `branch.organization_id == user.organization_id`.

**7.3 Action matrix (proposal).** AUDITOR: read-only. Upload / run analysis / review: OWNER, FINANCE_MANAGER,
ACCOUNTANT, OPS_MANAGER. Contracts, branches, users: OWNER (own org) and operator; contracts also
FINANCE_MANAGER. `/platforms` create: operator only. Organizations create: operator only.

**7.4 Enforcement.** One dependency produces an `AccessContext(user, role, org, branch scope)`; helpers
`require_branch / require_analysis / require_file / require_report / require_match / require_discrepancy` resolve
upward to branch → org in one join. Out-of-scope returns **404** (not 403) to avoid leaking existence; AUDITOR
writes return 403. List endpoints filter by scope; add `GET /auth/me/branches` and `GET /organizations` (own org;
operator: all). Unauthenticated allowlist: `/health`, `/auth/login`, `/auth/logout`; review what
`/deployment/info` and `/updates` expose before leaving them open.

**7.5 `POST /users`.** Auth required. Operator: create users in any org (incl. a new org's first OWNER).
OWNER: create users in own org only, never operators. Existing e2e tests that rely on open signup switch to a
seeded operator fixture.

**7.6 Migrations.** Alembic baseline `0001` = current models; prod is `stamp`ed, never re-created; CI check that
autogenerate against a `create_all` DB is empty. `0002`: enum value, `users.organization_id`, backfill of
existing users to the single existing org via an explicit command argument (no silent guessing; the operator
account is chosen by email), CHECK constraint, `audit_log.organization_id`. Start command runs
`alembic upgrade head` before uvicorn; `create_all` stays for SQLite tests only. Downgrade note: a PG enum value
cannot be removed. Verification: Postgres built from the *old* code → migrate → compare; plus a script you run
against a restored copy of a prod dump before touching prod.

**7.7 n8n (pending the JSON).** Browser sends the user's bearer token to the webhook; n8n validates it with
`GET /auth/me`, then uses that same token on every API call (session lifetime is 24 h, longer than a run). The
service-account login is removed from user-initiated runs; operator runs carry the operator's token, so the
audit trail shows the real person. The backend stays the final authority either way.

**7.8 Exit criteria.** All existing tests pass (updated); new cross-tenant matrix test per route; a test that walks
`app.routes` and fails if any route lacks an auth dependency outside the allowlist; migration test on SQLite and
Postgres; re-run of the four exploit probes against the patched instance (expect 401/403/404); a short list of
`curl` checks for you to run against live Render (I cannot reach it); zip delivery.
